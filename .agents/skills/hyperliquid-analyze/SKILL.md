name: hyperliquid-analyze
description: Analyze user-selected Hyperliquid crypto perpetual pairs on the specified OpenMarket chart using its three toolkits and current account state, producing evidence-backed intraday scenarios with entry, leverage, position size, SL and TP when warranted.
---

Read `AGENTS.md`, `PROFILE.md`, `config/profile.json`, `docs/analysis.md`, `docs/indicators.md`, `memory/lessons.md` and the latest relevant reviews/plans. Respond in French. The horizon is 15 minutes to several hours, maximum 24 hours. Read actual tool output; do not claim indicator observations from the attached source code.

Read `docs/browser.md` if browser calls fail, the selected ticker still has the previous pair's prices, or rounded/animated indicator values are ambiguous.

1. Resolve every requested pair to its exact Hyperliquid contract/DEX. Refresh metadata, context, margin tiers and book with `python3 scripts/desk.py market COIN --output .local/COIN-market.json`. Verify underlying/collateral, maximum leverage at the proposed size, and any existing exposure. Check previous scenarios for pending/triggered/missed/invalidated/expired state; a price touch proves neither a fill nor an actionable retest.
2. Visit **`https://openmarket.xyz/chart/FjCa6FS3`** in the connected browser. Select the requested contract in that chart. Verify venue, contract, timeframe and current data. Inspect 1h (4h if useful) for regime, 15m for structure and 5m for timing; use 1m only for a concrete execution question. Use **Price Action Toolkit**, **Trend Signals Toolkit** and **Oscillator Toolkit**. Record actual settings where they matter, last completed signal bar, visible levels and each toolkit's useful or conflicting observation. Screenshot the relevant view when useful. Do not alter indicator code or persist new settings merely to manufacture confluence. If the chart/panels are unavailable, finish an explicitly incomplete technical note but the actionable decision list remains empty.
3. Refresh `https://app.hyperliquid.xyz/portfolio` **Balances**, **Positions**, **Open orders**. Follow `docs/journal.md` for `state/account.json`. Balance/equity, collateral, mode, available-to-trade, order reservations and existing stop risk must be verified. Distinguish a flat account from failed retrieval. Existing positions and pending entries consume risk and may be correlated. Read-only API fallback is permitted when the user supplies their public address; unfamiliar unified/portfolio-margin availability requires UI verification.
4. Build a thesis from structure and regime. Identify invalidation first, then an entry with realistic limit-fill conditions, meaningful nearby target and expiry. Use each indicator as relevant; do not count their correlated price-derived outputs as independent votes. Check BTC/ETH market direction, liquidity, mark/book basis, funding and only news capable of affecting the holding window. Classify the result as `LIMIT_CANDIDATE`, `WAIT_EVENT`, `NO_TRADE` or `DATA_BLOCKED`. Reject stale breakouts, stop distances chosen to force large leverage, poor net reward/risk, unexplained data conflicts and insufficient exit liquidity.
5. Only for a supported candidate, populate `templates/plan.json` with real evidence and explicit cost assumptions. Choose a justified loss fraction **at or below 20%**, never automatically 20%. Use the risk calculator via `python3 scripts/desk.py size --plan <path> --market <fresh path> --output <path>`. It verifies freshness, precision, isolated liquidation, depth, margin, fees, aggregate risk and target allocation. Re-read its rounded prices and quantities, then reassess whether the rounded structure still makes sense. `BLOCKED` is not a tradable result. The calculator supports a new isolated position only; same-coin exposure needs a combined position model, not an invented empty account. Explain such a limitation and leave its size non-actionable.
6. Write `reports/analysis/<UTC timestamp>-<pair>.md` using `templates/analysis.md`. If multiple pairs survive, prioritize and explicitly state whether scenarios are alternatives or can coexist within the total risk budget. Save exact plan/calculation inputs for future review. Conditional entries need a trigger, cancellation rule and short expiry; refresh the account within 120 seconds, market/book within 60 seconds, chart within 5 minutes before returning a reviewable plan. Expired or missing inputs must remain conditional.

The final answer contains only supported decisions (possibly `[]`) and the material reason for waiting. For each actual candidate include side, entry/order type, rounded quantity, notional, margin, leverage and live cap, SL trigger and order type, TP allocation, net expected target payout (not a promised return), modeled loss in USDC and equity %, stressed loss, estimated liquidation/buffer, horizon, expiry and invalidation. Prefer one SL/TP unless structure supports more. Explain mark-trigger semantics and verify partial-fill protection before the user manually places an order. Do not place/cancel/modify trades, leverage or margin through tools.
