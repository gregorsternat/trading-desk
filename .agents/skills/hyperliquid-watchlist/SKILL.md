---
name: hyperliquid-watchlist
description: Build a current Hyperliquid crypto perpetual activity watchlist before a trading session, with broad API coverage and only session-relevant news. Use for what to watch, not trade entries or sizing.
---

Work in the trading-desk repository. Read `AGENTS.md`, `PROFILE.md` and the watchlist settings in `config/profile.json`. Infer session duration from the user or use the next 3 hours, stating the assumption. Report to the user in French.

1. Run `python3 scripts/desk.py watchlist`. Read the generated JSON coverage and Markdown, not only the top names. Every DEX must be inventoried. Distinguish active native crypto, HIP-3 crypto candidates, delisted contracts, non-crypto, unknown underlyings, illiquid markets and request failures. Resolve unknown plausible crypto underlyings from official deployer specifications; add a dated source to `config/asset-overrides.json`, then rescan if this changes eligibility. Never claim full crypto coverage while classification or retrieval gaps remain.
2. Rank activity at the session horizon: closed 5m candles, 15m/1h movement, 1h range, relative 1h volume against the preceding 23h, ATR, 24h liquidity and recent book spread. A large 24h move can be inactive now. Inspect the ranking for a one-candle spike, exhausted move or negligible depth. A high score is neither a buy signal nor a probability of success. Current OI is a level; an OI change needs two timestamped observations. Compare valid previous snapshots only when useful.
3. Check today's macro calendar and current crypto/venue events using web tools. Prefer the event owner's release (central bank, statistical agency, project, exchange/status page). Distinguish publication time, event time and timezone. Include a catalyst only if it can change liquidity, volatility or watchlist priority during this session and its claim is actually supported. Macro timing alone may justify a session caution, not a directional prediction. Record checked sources and time in a small companion `*-news.json` with `status: checked`, `events: []` if nothing qualifies; use `status: unavailable` if retrieval failed. No evidence is different from not checking.
4. Write a concise final session report in `reports/watchlists/<UTC timestamp>-session.md`, linking the collector report. Usually 3–8 pairs is enough; fewer or zero is valid. For each: exact contract/DEX, why active now, usable liquidity, and what would make it stop being worth watching. Include only relevant scheduled event times. Do **not** provide a long/short preference, entry, SL, TP, size or recommended leverage. Mention coverage gaps once, concretely.
5. Update `state/session.json` with report paths, observation times, session end, expiry (normally no more than 60 minutes), coverage status and `watchlist`. The dated reports are the history. On refresh, compare prior names and explain only material additions/removals. No trade execution or account read is needed for this skill.

Use the public API even if browser access fails. If the API fails, retain the prior report as stale and produce a data-blocked status; do not recycle it as current. A scan command alone leaves the news and human activity review pending and is not a completed skill run.
